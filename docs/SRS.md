# WeatherGPT — Software Requirements Specification

**Status: DRAFT — reconstructed from code; not user-approved.**

Baseline: repository source inspected on 2026-09-17, HEAD `e193ab9`. This is a proposed requirements baseline and gap register, not a certification of functionality or meteorological accuracy. Tests listed below were located in source, **not executed** for this documentation-only task. README aspirations do not establish implementation or acceptance.

## 1. Scope and stakeholders

The primary `frontend/` UI combines weather, conversational assistance, route-weather analysis, climate/NWP views and advisories. Java exposes weather/account/domain APIs; Python exposes agent/route APIs and a separate voice service. Intended audiences include general weather users, travelers and sector-advisory users; account/admin roles are implemented. Operational disaster-management use, official-agency endorsement and quantitative forecast accuracy are **not established**.

`frontend2/` is a separate chat-focused client; root `route_weather/` and `offline_weather/` are adjacent prototypes, not evidence that the primary UI supports every feature they contain. New nowcasting scope is not inferred from historical README claims.

## 3. Cross-cutting requirements (proposed; approval needed)

| ID | Acceptance criteria | Evidence / current limitation |
| --- | --- | --- |
| NFR-01 — Provenance | Every synthetic/fallback/advisory response and its UI presentation distinguish it from observations and official products. An unavailable feed must not mean “no hazard.” | FR-05–07; climate and NWP provenance is incomplete. |
| NFR-02 — Durable/private state | Approved production storage survives restart; account/route data has defined retention, isolation and deletion rules. | `backend/src/main/resources/application.properties` defaults to in-memory H2; J/`ingest/Wis2IngestionService.java` stores process-local state; `ML/main.py` overwrites shared `ML/map/` output. No durable production design established. |
| NFR-03 — Secure deployment | Secrets are externally managed without checked-in fallback values; intended public/protected APIs and CORS origins are reviewed; local testing cannot accidentally mutate deployed services. | J/`config/SecurityConfig.java`, `backend/src/main/resources/application.properties`, `frontend/src/config/api.ts`; production hardening needed, credential values intentionally omitted. |
| NFR-04 — Controlled validation | Relevant builds/tests run reproducibly with recorded environment, commands and results, without live provider calls unless explicitly authorized. | `AGENTS.md` lists source-verified commands and real test names. Existing route endpoint tests can write map artifacts. No universal passing-suite claim. |
| NFR-05 — Reliability/usability | Agree measurable latency, availability, forecast accuracy, accessibility and supported-language targets; verify them under provider outages and realistic load. | No approved quantitative targets or measured compliance identified; do not invent SLA/accuracy numbers. |

## 4. Decisions required before approval

1. Which climate/NWP features remain clearly labeled demonstrations, and which require real datasets?
2. Which official warning feed, licensing, provenance and update/expiry rules will be used?
3. Which UI is supported long-term; are prototype/offline features in scope?
4. Which deployment environments, persistent database, secret management and CORS policy are approved?
5. What are voice integration, model/provider, language, privacy/retention, accessibility and operational safety expectations?

See `docs/ARCHITECTURE.md` for implementation boundaries and deployment hazards. None of these gaps authorizes app-code changes by itself.
